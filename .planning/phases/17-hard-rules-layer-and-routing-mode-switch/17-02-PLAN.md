<resolved_decisions>

**1. RoutingOptions.Mode field vs direct config read (locked)**

Two options were considered:
- **A.** Add `mutable Mode : string` to the `RoutingOptions` CLIMutable record (line 76-82 of CompositionRoot.fs).
- **B.** Read `config.["Routing:Mode"]` directly in the `RoutingAlgorithmRegistration` factory (mirrors Phase 16 `config.["Routing:Judge:Enabled"]` at line 549).

**Decision: Option B (direct config read).** Reasons:
- Mirrors the existing Phase 16 idiom (zero learning curve).
- Avoids extending `RoutingOptions` record, which would require updating every `RoutingOptions` construction site in tests (`MLRoutingTests`, `CanaryTests`, etc.).
- A single string scalar is exactly the use case `config.[...]` is designed for.
- `CLIMutable` + `mutable` would work, but the test fixture churn isn't worth it.

**Source:** 17-RESEARCH.md "Open Questions" #2, Pitfall 2.

**2. Stub selfrouting algorithm in Phase 17 (placeholder until Phase 19)**

Phase 19 will ship the real `makeSelfRoutingAlgorithm` (35B classify call, prompt-hash cache, etc.). Phase 17 needs a placeholder that makes the mode switch functional WITHOUT requiring Phase 19's `SelfRouter` adapter.

The stub returns Qwen35B/Default — the existing v1.x default behavior. Hard Rules (Stage 0) still fires when keywords match. The behavior in `Routing.Mode="selfrouting"` mode in Phase 17 is therefore:
1. Stage 0 Hard Rules: keyword match → 122B (works because Plan 17-01 ships this).
2. Stage 1 model override: explicit `model=35b` → 35B (works — Plan 17-01 unchanged).
3. Stage 2 task table: known task → table-mapped model (works — Plan 17-01 unchanged).
4. Stage 3 algorithm (the stub): everything else → 35B/Default.

This is intentionally a regression in `selfrouting` mode for non-keyword non-override prompts — they ALL go to 35B (whereas v1.x ML routing might have routed some to 122B). Phase 19 fixes this with the real self-classify.

**Operator-facing note in CHANGELOG (Plan 17-03):** `[Unreleased]` will document that `Routing.Mode="selfrouting"` in Phase 17 is a transitional state — full selfrouting decisions land in Phase 19. If the operator wants v1.x ML behavior in the interim, they set `Routing.Mode="ml"`.

**3. configureServices alias (no migration in Phase 17)**

`configureServices` (CompositionRoot.fs line 1140) is a backwards-compat alias for `configureRequestPipeline`. Since `configureRequestPipeline` is the only function modified in this plan, the alias automatically inherits the Routing.Mode behavior. No alias migration needed. STATE.md pending todo "Remove configureServices alias after ModelsTests migration" remains future work (not blocking Phase 17).

**4. ML adapters stay registered in BOTH modes (MODE-03)**

The existing comment at CompositionRoot.fs line 337 says "ML wiring is unconditional." Phase 17 PRESERVES this — only the `RoutingAlgorithmRegistration.Algorithm` function branches on mode. ML DI registrations (`IEmbedder`, `IClassifier` keyed "baseline" + "canary", `RetrainingService`, `CanaryService`) all stay registered unconditionally.

Rationale: `RetrainingService` accumulates training data regardless of mode. If we gated ML DI registration entirely on `Routing.Mode="ml"`, the training dataset would stop growing in selfrouting mode, defeating the "ML stays warm for re-activation" design.

</resolved_decisions>
