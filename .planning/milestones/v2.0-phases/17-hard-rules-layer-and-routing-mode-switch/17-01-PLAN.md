**1. HR-03 vs HR-06 cascade ordering conflict (authoritative resolution)**

The two requirements appear contradictory:
- HR-03: "Hard Rules cascade position: Stage 0 — runs BEFORE explicit model override / explicit task / self-classify; any keyword match → immediate-122B"
- HR-06: "...explicit model override AND explicit task field both BYPASS Hard Rules"

**Resolution (per STATE.md design decision 5 — locked 2026-05-11 with operator):**

> "Cascade order (Phase 17 locks in code): Stage 0 Hard Rules → Stage 1 explicit model override → Stage 2 explicit task table → Stage 3 sticky session → Stage 4 self-classify (non-streaming only) → Stage 5 default 35B."

**Hard Rules wins (Stage 0).** HR-06 is misworded — the correct text should say "explicit model override bypasses self-classify and sticky" not "bypasses Hard Rules." This wording fix is applied to REQUIREMENTS.md in Plan 17-03; in this plan (17-01), Hard Rules is implemented as Stage 0 and the unit tests verify Hard Rule wins over model override.

**Concrete behavior:** A request like `{"model": "35b", "messages": [{"content": "LLVM optimization"}]}` routes to **122B** (Hard Rule fires), NOT to 35B. This is a safety mechanism — operators cannot accidentally bypass it via the `model` field. The selfrouting design doc §6,12 makes this rationale explicit: heavy-keyword prompts MUST land on 122B regardless of any other signal.

**2. RoutingOptions.Mode field vs config.["Routing:Mode"] direct read**

Not relevant to Plan 17-01 — Mode wiring lands in Plan 17-02. (Resolution there: direct config read, mirroring the Phase 16 `config.["Routing:Judge:Enabled"]` pattern.)

**3. Test prompt keyword overlap (verified)**

    ```fsharp
    module SmartRouter.Core.HardRules

    open SmartRouter.Core.Domain

    /// Default keyword list (HR-02: hardcoded, NOT operator-configurable).
    /// Safety mechanism — operators cannot misconfigure via appsettings.json.
    /// Source: .planning/docs/35b-selfrouting.md §6,12.
    /// Case-insensitive match — keywords are ASCII so OrdinalIgnoreCase is correct.
    let private keywords =
        [ "LLVM"; "MLIR"; "compiler"; "segfault"; "optimization"; "concurrency" ]

    /// Stage 0 pre-routing: case-insensitive keyword scan over all message content.
    /// Returns Some (Qwen122B, High, HardRule) if any keyword matches; None otherwise.
    /// Pure function — no IO, no DI, no mutable state. Synchronous (no task {}).
    /// Applies to both streaming and non-streaming requests (HR-05): the cost is
    /// O(prompt_length * 6) String.Contains comparisons; ~0ms for typical prompts.
    let applyHardRules (req: RouterRequest) : RoutingDecision option =
        let combined =
            req.Messages
            |> List.map (fun m -> m.Content)
            |> String.concat " "
        let matched =
            keywords
            |> List.exists (fun kw ->
                combined.Contains(kw, System.StringComparison.OrdinalIgnoreCase))
        if matched then
            Some { Target       = Qwen122B
                   Priority     = High
                   Reason       = HardRule
                   IsFallback   = false
                   ModelVersion = "" }
        else
            None
    ```

    Notes:
    - **ARCH-01 compliant:** BCL-only (`System.String.Contains`, `System.StringComparison`); no Serilog, no HttpClient, no Microsoft.ML, no ASP.NET.
    - **ARCH-02 compliant:** No `async {}` or `task {}` — pure synchronous function.
    - **No catch-all arms anywhere** — preserves compile-time DU exhaustiveness checks.
    - `ModelVersion = ""` matches the existing convention for non-ML stages (see Domain.fs line 75: `""` is the sentinel that ChatCompletions falls back to `IModelVersionProvider.CurrentVersion`).
